Drive any coding agent through structured, multi-step workflows.

How It Works

Prompt Stack sits between you and the agent.

You (or CI)

↔

Prompt Stack

↔

Any Agent

Claude, Codex, GPT, Gemini

→ Reveals one step at a time
← Agent reports what it found
↻ Checks coverage. Loop or advance.

You define the workflow. Prompt Stack drives the agent through it step by step, checks the output after each round, and decides whether to keep going or move on. The agent does the work. Prompt Stack makes sure the work is thorough.

The Problem

Agents finish as fast as possible.

You Design a caching strategy for our API. Consider Redis vs Memcached, invalidation patterns, and scaling to 10M requests/day.
Agent For your API caching strategy, I recommend Redis over Memcached due to its richer data structures and built-in persistence. Here's my approach:

Layer 1: Application Cache — Use Redis with a TTL-based invalidation pattern. Set TTLs based on data volatility: user profiles at 5 minutes, product listings at 1 hour, static content at 24 hours.

Layer 2: CDN Edge Cache — Put Cloudflare or Fastly in front of your API for read-heavy endpoints. This handles 60-70% of traffic before it hits your servers.

Scaling Strategy — At 10M requests/day (~115 RPS average), a single Redis instance handles this easily. Use Redis Cluster if you need to shard across multiple nodes for write-heavy workloads...
...continues for 800 more words
30 seconds. Looks done. One approach. No pushback. No coverage check.
  • Used one approach. Never considered failure modes or team capacity.
  • Never challenged its own answer. Nothing pushed back.
  • Stopped because it ran out of things to say, not because it covered what matters.
The Fix

What happens when Prompt Stack drives the conversation.

The workflow has 3 steps. The agent sees one at a time.

Multi-step workflows

Prompt Stack Step 1: Analyze the architecture decision. Report what you found and what's still unexplored.
Agent I analyzed using cost-benefit. Here's what I found: Redis wins on features, Memcached wins on simplicity. Still unexplored: failure modes, team capacity, long-term maintenance.
Prompt Stack Step 2: You missed failure modes. Assume this fails in 6 months. What went wrong?
Agent Three failure scenarios: cache stampede during deploys, stale data serving after partial invalidation, and Redis memory exhaustion during traffic spikes. The original recommendation doesn't account for these.
Prompt Stack Step 3: Produce the final recommendation incorporating all findings.
Agent Revised recommendation: Redis with circuit breakers, write-behind invalidation, and a memory budget with eviction policies. Fundamentally different from the initial "just use Redis with TTLs" answer.
After each round, Prompt Stack checks: has enough ground been covered?

The system decides when you're done, not the agent

Watch It Work

Should we build or buy?

A real decision. Three rounds. One answer you'd actually bet on.

Your team needs a notification system. Build it in-house or use a vendor like Twilio? Budget: $50K/year. Team: 4 engineers.
The obvious answer

Round 1 — First Pass

Build in-house. Lower long-term cost, full control, custom integrations. Estimated 6 weeks to MVP.

This changes the recommendation

Round 2 — Different Approach

Prompt Stack pushed for total cost of ownership. 6 weeks to build + 20% of one engineer's time for maintenance + on-call burden + scaling costs at 10x growth. Vendor: $12K/year, zero maintenance. The 3-year cost comparison flips.

This risk was invisible in Round 1

Round 3 — Stress Test

Prompt Stack asked: what if the lead engineer leaves? Now you have a custom system nobody fully understands, no documentation, and a vendor migration under pressure. The risk wasn't in the cost model — it was in the bus factor.

The answer worth betting on

Final Output

Use Twilio for transactional notifications. Build a thin integration layer for custom routing. Migrate to in-house only if vendor costs exceed $40K/year AND team grows to 6+. Here's the migration path.

Round 2 changed the math
Round 3 found the risk no one asked about
The final answer is fundamentally different from Round 1

How It Actually Works

Everything above is powered by YAML definitions and a loop primitive.

name: arch-interview
entry: ask
nodes:
  ask:
    type: action
    op: lev.exec
    loop_until: "status == 'complete'"
    loop_max: 20
    next: emit
  emit:
    type: action
    op: lev.exec
    terminal: true

Two nodes. One loops until coverage criteria are met.

Orchestrator ↔ prompt-stack CLI ↔ Agent ↔ Architect (via lev exec)

loop_until

Runtime evaluates structured outputs against exit conditions.

Dimension tracking

12 exploration dimensions, completeness gate.

Framework rotation

19 named analytical approaches, varied per round.

Exec bridge

Dispatches to any CLI runner.

Active-step-only

Agent sees one step. Can't race ahead.

Filesystem state

Each round writes to disk. Fresh context, no degradation.
